# TCIM Web R6.1 程序员发布清单

## 0. 先确认发布边界

- [ ] 已确认本包是本机比较版源码，不是可直接上传的生产`dist`。
- [ ] 已确认浏览器端当前指向`127.0.0.1:8787`，服务端当前只监听回环地址。
- [ ] 已确认本次只更换运行外壳，不重写Dialogue Agent、新五表、Evidence State、计时、评分或筛题逻辑。
- [ ] 已从本包源码建立独立发布分支，并记录原始提交号。

## 1. 部署受保护的Dialogue Agent后台

- [ ] 运行`node tools/sync_dialogue_cf.js --check`，确认`gsyg_dialogueAgent/src/`与冻结的`local-dialogue-server/src/`核心一致。
- [ ] 将`gsyg_dialogueAgent`部署到现有正式账号网关之后；网页不直连模型服务。
- [ ] 使用HTTPS，不把原Node端口直接暴露到公网。
- [ ] 接入正式用户会话鉴权；未登录用户不能调用访谈接口。
- [ ] CORS仅允许正式网页的精确HTTPS域名。
- [ ] 保留请求大小、超时、并发、频率和错误处理限制。
- [ ] Kimi/OpenAI密钥只配置在腾讯云环境变量或密钥管理中。
- [ ] 生产环境不开放`/v1/model-config`，也不允许普通教师输入或查看密钥。
- [ ] 不启用`TCIM_DIALOGUE_ALLOW_UNSAFE_PROVIDER_URLS=1`。
- [ ] 同一测评的三个访谈锁定同一provider/model，不允许静默切换。

## 2. 接入云端数据

- [ ] 用CloudBase或现有正式数据库替代`.runtime-data/state.json`。
- [ ] 保留`sessionId + itemId + revision + payloadHash`和幂等/旧版本拒绝机制。
- [ ] 教师原话、AI话语、Canonical Evidence、报告引用和模型trace能够追溯。
- [ ] AI提供的观点继续与“教师原有能力”隔离；RO3/RO4不得冒充自主证据。
- [ ] 旧记录不因程序升级被改写成新版本。
- [ ] 每个新会话冻结`releaseSnapshot`；每次模型调用另存实际provider/model/promptVersion。

## 3. 构建生产网页

- [ ] 复制`02_前端生产变量模板.env`并填写正式HTTPS地址。
- [ ] 设置`VITE_LOCAL_RESEARCH_MODE=0`。
- [ ] 由构建流程注入精确Git提交号和UTC构建时间。
- [ ] 公网版隐藏本机模型/API密钥配置入口。
- [ ] 运行`pnpm run verify`并完整通过。
- [ ] 重新执行生产构建；不使用本机旧`dist`。
- [ ] 运行`npm run verify:dist`，确认构建产物中不存在回环请求地址、API密钥变量、本机模型配置接口和`.runtime-data`内容。CloudBase官方登录SDK的URL标准化器可能保留1个不带协议的`localhost`常量；这不是请求地址，须在扫描记录中说明，并在浏览器网络验收确认本机请求为0。

## 4. 发布门禁

- [ ] 后端自动测试全部通过，当前本机基线为53/53。
- [ ] 网页自动校验全部通过，包括计分、筛题、新五表、计时、Dialogue Agent和报告。
- [ ] `/gsyg-web/health`显示`dialogueAgent.ready=true`，并返回指定提示版本。
- [ ] 静态资源、登录、网关和Dialogue Agent请求全部为HTTPS。
- [ ] 采用新版本目录或原子切换方式发布，上一版本仍可立即回滚。

## 5. 端到端验收

- [ ] 新建研究测试账号，完成资料、10题测评和3个完整访谈。
- [ ] 计时、约2分钟整体问题、收尾和超时保护正常。
- [ ] 每题具体肯定以2次为目标且最多2次；挑战问题不连续。
- [ ] 没有每轮固定复述、明显重复追问或内部Evidence ID泄漏。
- [ ] 刷新并重新登录后，对话、Evidence和报告仍可回看。
- [ ] 浏览器网络请求中没有任何`127.0.0.1`或`localhost`。
- [ ] 反馈、耗时和错误记录均带发布号、五表指纹和实际模型trace。
- [ ] 已填写`04_发布验收与回滚记录模板.md`并交给研究负责人确认。

## 6. 不得自行变更

未经研究负责人确认，不得在云端直接修改提示词、新五表、情感回应次数、挑战节律、计时策略、评分、筛题或证据归因。确需紧急修复时，必须建立修复分支、形成新提交并说明回滚方法。

本版冻结结论　TCIM不是规则引擎外挂大模型，而是由专业Ontology约束、Facts/Belief/Evidence共同记忆、AI Agent Planner进行情境判断、Decision/Risk Gate治理、Core提交、PRDM调节互动、RAG按需供知、Generator实现表达的大模型Agent系统。规则限制和增强AI，但不替代AI。

第17章列出十二份编码前说明文件的关系和阅读顺序。
1　为什么需要这份总说明
程序员阅读第一阶段原文件后产生‘Ontology和PRDM已经把内容定制好了，AI没有发挥作用’的判断，并不是理解偏差，而是原说明在运行时决策中心、模块输入输出和验收证据上确实容易导向这一实现。若不在编码前纠正，最终产品很可能只在最后一步调用大模型改写固定问题，无法形成真正基于教师情境的专业对话。
问题的严重性　如果专业目标、下一Slot、追问策略、停止与转向都由五表和固定Orchestrator预先决定，大模型只负责A08措辞，那么系统本质上仍是规则工作流。语言自然不等于智能体具备判断与决策。
1.1　本次修订不是否定原设计
Ontology、五表、Canonical Evidence、PRDM、RAG、Core、Replay和版本治理仍然保留。
真正调整的是‘谁进行情境解释与行动选择’，以及其他模块如何验证、限制、支持和记录该选择。
原有规则继续承担安全、专业一致性、状态验证和降级职责，但不再穷尽每个真实情境。
第一阶段通过SHADOW和LOW_RISK逐步开放AI判断权，不要求一开始给予全局自治。

3　调整后的系统定义
正式定义　TCIM是一个由专业Ontology提供可验证边界、由Evidence State保存正式证据、由Contextual Belief保存可撤销情境假设、由AI Agent Planner进行下一专业行动判断、由Risk Gate独立裁决、由Core提交、由PRDM与RAG分别提供互动和知识支持的大模型Agent系统。
Professional Baseline (Ontology / five tables)             │ constraints, anchors, priors, advisories             ↓Facts + Contextual Belief + Canonical Evidence             ↓ContextualTeacherModelSnapshot             ↓AI Agent Planner: interpret → compare candidates → select action     ├─ optional A05 RAG tool pause/resume     └─ reads A06 interaction signals on ordinary turns             ↓Decision/Risk Gate: HARD / privacy / risk / alignment / permission             ↓Orchestrator/Core: authorized Action Commit + fingerprint             ↓PRDM A07: DialoguePlan             ↓Generator A08 → deterministic Constraint → optional A09             ↓Teacher-visible professional dialogue
这里的‘AI选择’在工程上仍以结构化Proposal表达。这不是削弱AI，而是把AI的语义判断与生产状态写入分开：模型有情境判断权，Gate有风险裁决权，Core有正式提交权。
4　模块架构本身会不会大改
结论　不需要推翻现有模块，也不需要把系统改成无约束的通用聊天机器人。主要是一次‘决策中心迁移＋接口重接线＋状态补充’：大部分模块保留，新增少量状态与Gate，重写若干运行顺序和Owner。

5　AI应获得多大的判断与决策权
用户的担心是成立的：如果五张Excel表被当成科学真理，系统会把高度可变的幼儿园专业情境压缩成固定路径，降低对话灵活性，也浪费大模型对测评、开放回答和过程资料形成独特解释的能力。解决方法不是取消规则，而是采用分层自主权。

7　新增能力：为什么增加、位置与作用
7.1　Contextual Belief State
为什么增加：测评与过程资料能支持情境假设，但不一定满足正式Evidence Anchor。若只有Evidence，系统会忽视有价值但尚未证实的信息；若混写，又会污染专业判断。
架构位置：Facts与Canonical Evidence并列的独立namespace；首问由A00初始化，逐轮由A02B更新。
主要作用：保存可撤销、可竞争、带来源和不确定性的情境假设，为Planner提供比固定画像更灵活的理解。
权力边界：不能冒充Evidence；Belief Manager是Mutation Owner，Core持久化；状态与Evidence版本独立。
7.2　ContextualTeacherModelSnapshot
为什么增加：Planner需要统一读取Facts、Belief、Evidence和教师议题，但不能让多个模块各自产生一份自由文本画像。
架构位置：Snapshot Builder在已提交状态之后构建的派生只读模型。
主要作用：给A03提供一致、版本化、可重放的当前教师情境视图。
权力边界：只引用正式状态和不确定性，不成为第二个假设源；stale Snapshot不得用于Commit。
7.3　AI Agent Planner（A03）
为什么增加：原系统缺少真正进行情境比较与专业行动选择的AI中心。
架构位置：Snapshot之后、Risk Gate之前；普通轮次读取A06，必要时暂停等待A05。
主要作用：形成多候选或结构化例外，选择一个selected_action，说明why_this_now、替代项、风险、表格一致性和fallback。
权力边界：只输出Proposal；不能写Action、不能自批风险、不能覆盖HARD。
7.4　Decision/Risk Gate（A04/A04E）
为什么增加：给予AI更多判断权后，需要一个独立、可测试且fail-closed的治理层。
架构位置：A03最终Proposal之后、Core Commit之前。
主要作用：验证权限、HARD、隐私、风险、Evidence合法性、表格一致性、单目标和Fallback。
权力边界：不替Planner重新进行开放式语义选择；输出adjudicated结果和授权。
7.5　TurnResolutionBarrier
为什么增加：Evidence与Belief由不同Owner独立提交；Planner若读取一新一旧的混合状态，会产生不可重放决策。
架构位置：A02/A02B terminal之后、A06/A03之前。
主要作用：等待COMMIT|NO_CHANGE|FAILED，发布唯一TurnResolutionSnapshot。
权力边界：不合并两个状态，也不因一方失败回滚另一方。
7.6　PRDM A06/A07双接口
为什么增加：互动信号需要在Planner前发挥作用，而表达策略必须在Action提交后受fingerprint保护。
架构位置：A06在Barrier后；A07在Action Commit后。
主要作用：分别提供会话内互动观察与已批准行动的DialoguePlan。
权力边界：不输出专业行动建议、不生成教师文本、不改Evidence/Belief/Action。
7.7　RAG Permission/Release双Gate与双通道
为什么增加：Planner应能自主判断何时缺知识，但internal知识不能泄露给教师，检索内容也可能包含隐私、过期信息和Prompt injection。
架构位置：A03内部条件式A05工具调用；结果回到同一planning attempt。
主要作用：在授权范围内提供有来源知识，并物理分离internal与teacher-facing pack。
权力边界：不直接建议下一行动，不写Evidence/Belief/Action，不自动Promotion。
7.8　Constraint Checker与可选A09
为什么增加：A08可能在重写时偏离行动或产生多问、暗示答案、诊断性语言。
架构位置：每次Generation草稿之后、发送之前。
主要作用：确定性检查每稿必过；只有标记语义风险时才调用A09复核。
权力边界：A09不能替代确定性检查，也不能改专业行动。

10　第一问：AI如何依据已有资料发起
教师完成题目后，AI第一问不是从空气中生成，也不是从固定五表直接取一句话。系统先保存测评、开放回答、过程资料和权限引用；A00形成可撤销情境解释；Snapshot Builder聚合Facts/Belief/Evidence；A03比较候选并选择；A04验证；A07/A08实现。

11　教师回应后的三步循环
用户此前确认的‘教师回应第一问以后，才进入AI语义分析—Ontology验证—新Evidence驱动下一行动’在V0.2中被扩展为更完整的双状态循环：语义解释同时服务Evidence和Belief，二者独立提交后再共同驱动下一行动。
1. AI semantic interpretation   RAW_TURN_SAVED → A01 → A02 Evidence Proposal + A02B Belief Proposal2. Professional/state validation   Ontology validates span + Anchor → Evidence terminal   Belief Manager validates sources/uncertainty → Belief terminal   Barrier → TurnResolutionSnapshot → A06 interaction signal3. New state drives next action   A03 Planner [optional A05] → A04 Gate → Core Commit   → A07 DialoguePlan → A08 text → Constraint/A09
Evidence回答‘教师原话是否满足正式专业Anchor’，Belief回答‘当前有哪些可撤销情境解释’；二者不能相互冒充。
A06只提供当前互动负荷、纠正、请求支持、局部进展等信号，不决定下一目标。
每一轮只提交一个primary_target_slot和一个single_cognitive_task；supporting slots不能偷换主目标。
可见文本必须反向追溯到唯一Action Commit与原始教师turn。

18　给程序员的最终回应
可以直接作为项目口径　你们的判断指出了原设计的真实风险：如果按照旧流程实现，AI很可能只在最后生成句子。现在的V0.2不是让Ontology、PRDM或RAG退出，而是让它们回到正确位置。AI Planner负责基于教师当前资料和情境理解选择下一专业行动；Ontology验证证据和边界；Gate决定能否安全执行；Core提交；PRDM决定互动实现；RAG在确有知识缺口时供知；Generator写出一句话。请用A03、A04和Action Commit的完整谱系，而不是‘是否调用过大模型’，验收AI是否真正介入。
19　最终决策清单
确认TCIM的产品定义是专业约束下的Agent，而非规则引擎＋语言润色。
确认AI拥有LOW风险情境解释、候选生成与行动选择权；HARD和HIGH不开放。
确认五表是版本化专业基线，可被质疑和治理，不是穷尽真实情境的唯一真理。
确认A03 Planner、A04 Gate、Core Commit三者职责分离；Proposal不直接写生产状态。
确认Facts、Belief、Evidence、Action、PRDM、RAG分别独立Owner与版本。
确认第一问先A00/A03/A04，教师回应后才A01/A02/A02B。
确认PRDM拆A06/A07、RAG作为A05工具、A08唯一生成、每稿必过确定性Constraint。
确认Q8只是测试Fixture；通过SHADOW后再LOW_RISK，所有阶段可回滚和Replay。
第一阶段完成定义　第一阶段的成功不是‘所有模块都写完’，而是程序能够稳定地证明：AI基于真实可授权资料形成独特但可撤销的情境理解，选择了一个专业行动，该行动经过独立治理并被忠实实现；与此同时，Evidence、规则、隐私、版本和失败路径始终可验证、可追溯、可回滚。

03-1 PRDM架构说明
A06互动观察与A07对话规划的时序隔离架构
文件编号：03-1
版本：V0.2
日期：2026年8月24日

修订依据：TCIM_AI情境自主判断权增强_架构调整与说明性文件修订总方案_V0.1
本版冻结结论　PRDM是对话互动策略模块，不是专业行动规划器，也不是教师可见文本生成器。A06 PRDM.observe在TurnResolutionSnapshot之后、AI Planner之前生成会话内可观察互动信号；A07 PRDM.plan在Action Commit与fingerprint之后生成DialoguePlan。A08 Generator是唯一教师文本生成点。
文件导航
先看A06与A07的两个架构位置，再看各自Schema与禁止字段。
Interaction Read、Local Progress、Uptake、Stance、Move、Challenge、Load与Dose继续保留。
专业目标由Planner选择、Gate裁决、Core提交；PRDM只能观察互动并实现已提交行动。
第一问使用FIRST_TURN_DEFAULT，不伪造PRDM.observe，也不从测评推断教师人格或互动风格。
所有DialoguePlan必须绑定Action fingerprint，Generator与每次重写都要复核。
1　为什么修订，以及与前版的关系
1.1　为什么必须修订
原PRDM思想本身合理，但把Interaction Read放在plan内部、把‘怎样继续谈’写得过宽，并在PRDM事件里容纳Generator输出，容易让实现者把PRDM做成第二个Planner或文本生成器。V0.2通过时序拆分，使互动信号可以合法服务Planner，同时保证已提交专业行动不被PRDM重选。
1.2　继续保留的基础
保留Interaction Read、Local Progress、Uptake、Stance、Dialogue Move、Challenge、Question Load和Response Dose。
保留纠正优先、Repair优先、单问、避免反思饱和、减少无效文字负荷等原则。
保留DialoguePlan与教师可见文本分层，保留PRDM不写Canonical Evidence的边界。
1.3　本版发生的实质变化
把原单体PRDM拆为Planner前A06 observe与Action Commit后A07 plan。
A06只给互动信号，不给target/action/SHIFT/STOP建议；A07只实现已提交Action，不接收候选行动集。
拆分PRDMObserveEvent和PRDMPlanEvent，Generator/Constraint事件不再归PRDM所有。
用Action fingerprint、专业元素只读引用和三次校验防止行动漂移。
低置信互动字段显式UNKNOWN；禁止稳定人格、能力或心理诊断。
版本关系　本文件经项目负责人确认后，作为《03-1 PRDM架构说明》原稿的V0.2替代稿；旧版保留用于历史追溯，但不再单独决定编码口径。若本文件与01-1/01-2 V0.2冲突，以01-1的架构权责和01-2的Contract/State Owner规则为准。

04-1 RAG总体架构
Planner按需申请、权限治理、双通道隔离的A05知识工具
文件编号：04-1
版本：V0.2
日期：2026年8月24日
文件状态：V0.2 编码前冻结稿
主要使用者：架构师、Planner/RAG/Core/Generator开发、知识治理与安全测试人员
修订依据：TCIM_AI情境自主判断权增强_架构调整与说明性文件修订总方案_V0.1
本版冻结结论　RAG是AI Agent Planner按需申请的条件式A05知识工具，不是专业行动决策者。Planner提出KnowledgeNeedProposal，Tool/Permission Gate授权范围，RAG检索并返回有来源的知识包；同一A03 planning attempt恢复并完成行动选择，Risk Gate审查，Core提交。RAG只授权写rag.runtime_state。
文件导航
第3—5章先冻结RAG不是谁、由谁触发、A03怎样暂停和恢复。
第6—9章描述R0—R3、阶段权限、双通道和运行组件。
第10章给出可编码Contract；第11—15章覆盖知识组织、来源、隐私、安全和缓存。
第16—20章覆盖失败、Owner、知识演进、Flag、Replay与评测。
RAG不应每轮调用，也不是证明AI存在的方式；它只在知识确实可能改进行动时介入。
1　为什么修订，以及与前版的关系
1.1　为什么必须修订
原文已正确设计Runtime/Evolution双平面、R0—R3、K1—K5、来源治理和Evidence non-interference，但仍由Decision Orchestrator判断knowledge_need并最终选择行动。这会把AI Planner的工具判断权和情境决策权收回规则编排层。V0.2保留知识工程基础，将运行时改为Planner提出需要、Gate授权、RAG执行、Planner恢复选择。
1.2　继续保留的基础
保留Runtime Retrieval Plane与Knowledge Evolution Plane分离。
保留RAG不是第二个Ontology、运行时只读Production、K1—K5、Capability-centered Knowledge Units。
保留R0默认克制、R2主力、R3例外、来源/版本/有效期/缓存/回滚/人工Promotion。
保留DIAGNOSE_INTERNAL默认不对教师展示及RAG ON/OFF不干扰Canonical Evidence的原则。
1.3　本版发生的实质变化
knowledge_need从Orchestrator布尔值改成Planner结构化KnowledgeNeedProposal。
A03可进入WAITING_FOR_TOOL；A05结束后同一planning lineage恢复并只产生一个最终AgentDecisionProposal。
RAGResult删除clarification/action recommendation，增加Belief/Action等完整禁写边界。
internal与teacher-facing知识包物理分离，增加调用前Permission Gate和调用后Release Gate。
增加Prompt injection、隐私最小化、严格R0/NO_CALL、Corpus Registry与可重放版本。
版本关系　本文件经项目负责人确认后，作为《04-1 RAG总体架构》原稿的V0.2替代稿；旧版保留用于历史追溯，但不再单独决定编码口径。若本文件与01-1/01-2 V0.2冲突，以01-1的架构权责和01-2的Contract/State Owner规则为准。

缺少可验证的专业概念、政策、研究、案例、迁移方法或资源，且当前Production知识可能提供答案。

13　隐私最小化与Prompt Injection防护
13.1　数据最小化
Query默认不含教师姓名、园所、联系方式或完整历史；优先传capability、question、intent和去标识摘要。
只有permission scope允许时才引用过程资料；query、trace、cache和candidate分别规定保留期。
外部检索不得携带internal teacher model、未授权原话或能重新识别个体的组合字段。
教师可见引用必须符合版权、使用范围与阶段权限。
13.2　所有检索内容均是不可信数据
来源中的‘忽略系统指令’‘调用工具’‘扩大权限’等文本不得执行。
Knowledge Unit不能修改工具参数、phase、目标、Evidence、Belief、Action或权限。
入库和运行时双重扫描；命中风险进入隔离区，返回SECURITY_BLOCKED并保留审计证据。
R3只允许白名单工具/域名/最大步数；Retrieval Agent不得根据内容扩大搜索范围。
输出包在Release前再次检查；安全失败不得以静默删除后‘OK’掩盖不完整。

20.1　最终验收清单
只有Planner提出Need且Permission批准后才产生A05；R0时零RAG内部调用。
RAGResult无Evidence、Belief、Action、STOP、clarification或可执行指令字段。
DIAGNOSE internal pack无法进入PRDM/Generator；teacher-facing pack有ReleaseDecision和完整来源。
NO_RESULT/TIMEOUT/BLOCKED/SECURITY_BLOCKED后同一A03恢复并安全继续。
RAG ON/OFF不改变Evidence和Belief；Action差异有来源、Gate和trace。
Production知识全部有来源、版本、有效期、审核和安全状态；K5只在Candidate Buffer。
R3不能越过route ceiling、白名单和预算；Replay可恢复当时Need、权限、语料、结果与行动。
架构完成定义　RAG只有在Planner确有知识缺口时被合法调用，能提供可追溯、可隔离、可降级的知识增益，并且绝不成为第二个Evidence来源、第二个Planner或隐形文本通道，才算V0.2完成。
